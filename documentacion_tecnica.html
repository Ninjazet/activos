Cómo funciona GestActivos

Una guía práctica para que otro programador pueda instalar, recorrer, mantener y ampliar el sistema sin tener que deducir cada flujo desde cero.

PHP 8 + PDO MariaDB / MySQL Bootstrap 5.3 jQuery + AJAX TCPDF XAMPP
01 · Propósito

Qué resuelve el sistema

GestActivos administra empleados, equipos, catálogos, usuarios, permisos y el ciclo completo de entrega y devolución de activos.

Inventario

Registra cada equipo con código interno, serie, tipo, datos de compra, garantía y estado operativo.

Custodia

Relaciona un equipo con un empleado, deja constancia de las condiciones de entrega y cierra la asignación al devolverlo.

Control

Limita cada módulo mediante permisos, registra acciones relevantes en bitácora y produce consultas, reportes y actas PDF.

02 · Inicio rápido

Levantar el proyecto localmente

  1. Coloque el proyecto en C:\xampp\htdocs\activos.
  2. Inicie Apache y MySQL/MariaDB desde XAMPP.
  3. Compruebe en config/database.php que la base sea gestactivos, el host localhost y que las credenciales coincidan con su servidor.
  4. Importe el respaldo actual de la base. No ejecute las migraciones históricas sobre una base ya actualizada sin revisar antes su contenido.
  5. Abra http://localhost:8080/activos/ si Apache usa el puerto 8080, o http://localhost/activos/ si usa el puerto 80.
  6. Inicie sesión con un usuario existente de la base. No hay credenciales universales codificadas en la aplicación.

Configuración principal

  • config/app.php: nombre, versión, URL base, zona horaria y carpetas de imágenes.
  • config/database.php: conexión PDO.

Requisitos de escritura

El usuario de Apache debe poder escribir en las carpetas configuradas para fotografías y firmas. Los archivos subidos se guardan con nombres aleatorios.

03 · Arquitectura

Modelo mental del proyecto

No utiliza un framework MVC. Es una aplicación PHP modular donde cada página actúa como controlador de entrada, las clases comunes concentran infraestructura y los archivos AJAX devuelven HTML parcial o JSON.

Navegador
GET, formulario POST o petición AJAX.
Página PHP
Carga bootstrap, valida sesión y permiso.
Controlador
Valida CSRF y datos; aplica reglas.
Database/PDO
Consulta o modifica MariaDB, con transacción si corresponde.
Respuesta
Vista completa, fragmento HTML, JSON, redirección o PDF.

Las cuatro capas que sí existen

CapaUbicaciónResponsabilidad
Arranque e infraestructurabootstrap.php, config/, app/core/Constantes, conexión, sesión, autenticación, CSRF, cargas y utilidades.
Controladoresapp/controllers/Procesan altas, cambios, activaciones, inactivaciones y reglas de negocio.
Vistas y fragmentosArchivos raíz, app/pages/, app/ajax/Construyen páginas, formularios, tablas, modales y respuestas AJAX.
Documentosreportes/, public/lib/tcpdf/Consultas imprimibles, exportaciones y actas con firma.
Importante. No asuma que el nombre “controlador” implica separación completa de HTML y lógica. Antes de modificar una función, siga la ruta desde la página principal hasta su controlador y su archivo AJAX.

05 · Orden de lectura

Cómo entender el código sin perderse

  1. Empiece por bootstrap.php. Así sabrá qué constantes y clases están disponibles en cada solicitud.
  2. Lea app/core/Auth.php y app/core/Database.php. Son las dependencias transversales.
  3. Revise login.php y index.php. Muestran el inicio de sesión, la estructura de sesión y el uso de permisos.
  4. Siga un módulo sencillo. Empleados o equipos muestran bien el patrón de formulario → controlador → tabla AJAX.
  5. Deje asignaciones para el final. Es el flujo más delicado porque coordina empleado, equipo, firmas, fechas, estados y transacciones.
  6. Lea los reportes después del flujo principal. En su mayoría consultan los mismos datos y los presentan mediante TCPDF.
Técnica recomendada. Busque el nombre del campo de base de datos que desea cambiar. Eso revela todas las pantallas, validaciones, consultas y reportes que dependen de él.
06 · Núcleo y funciones

Clases que usa todo el sistema

app/core/Database.php

Implementa una única conexión PDO mediante el patrón singleton. Los controladores deben enviar parámetros a consultas preparadas; no deben concatenar valores del usuario en SQL.

MétodoUso
Database::getInstance()Obtiene la conexión compartida.
consulta($sql, $params)Ejecuta SELECT y devuelve el statement.
fila($sql, $params)Devuelve una sola fila asociativa.
contar($sql, $params)Devuelve un valor de conteo.
ejecutar($sql, $params)Ejecuta INSERT, UPDATE u otra escritura.
transaccion($callback)Confirma si el callback termina y revierte si lanza una excepción.
 
<?php
$db = Database::getInstance();
$empleado = $db->fila(
    'SELECT * FROM empleados WHERE idempleado = :id',
    ['id' => $idEmpleado]
);

app/core/Auth.php

FunciónQué garantiza
Auth::iniciar()Inicia la sesión con sus parámetros de seguridad.
Auth::requerir()Redirige al login si no existe una sesión válida.
Auth::requerirPermiso('reportes')Bloquea la ruta cuando el permiso no está habilitado.
Auth::requerirPermisoActas()Permite abrir actas a usuarios con actas o con transacciones.
Auth::csrfField()Imprime el input oculto que debe llevar cada formulario POST.
Auth::verificarCsrf()Rechaza POST sin token válido.
Auth::flash() / obtenerFlash()Transporta mensajes entre una escritura y la redirección siguiente.
Auth::hashPassword() / verificarPassword()Genera y comprueba hashes seguros; nunca se guarda la contraseña legible.
Auth::bitacora()Registra usuario, acción, módulo, detalle, IP y fecha.

El login limita intentos fallidos a 5 dentro de 15 minutos, regenera el ID de sesión y actualiza hashes antiguos cuando PHP recomienda un rehash.

app/core/Upload.php

Valida que el archivo sea una imagen real, limita el tamaño a 5 MB, admite JPG/PNG/GIF/WEBP y genera un nombre aleatorio. Toda carga nueva debe reutilizar esta clase en lugar de confiar en la extensión proporcionada por el navegador.

07 · Flujos HTTP

Tipos de solicitud que verá en el proyecto

Página completa

Incluye bootstrap.php, exige permiso y carga encabezado, menú lateral, contenido y scripts. Ejemplo: empleados, equipos y panel principal.

Formulario POST

El controlador valida sesión, permiso, CSRF, campos y reglas; escribe, registra bitácora, crea un mensaje flash y redirige.

AJAX HTML

Recibe búsqueda o identificador y devuelve una tabla o formulario que jQuery coloca en #datos.

AJAX JSON

Los catálogos contextuales responden un objeto con éxito, mensaje e identificador para actualizar un selector sin recargar.

PDF

Una ruta de reportes consulta datos y entrega el binario con las cabeceras apropiadas; no debe haber salida antes de TCPDF.

Firma

El canvas produce una Data URI. PHP comprueba formato, tamaño, MIME y dimensiones antes de guardar la imagen y actualizar la asignación.

Plantilla segura para una escritura

<?php
require_once __DIR__ . '/../../bootstrap.php';
Auth::requerirPermiso('datosmaestros');

if ($_SERVER['REQUEST_METHOD'] !== 'POST') {
    http_response_code(405);
    exit('Método no permitido');
}

Auth::verificarCsrf();
// 1. Normalizar y validar entrada.
// 2. Consultar conflictos y dependencias.
// 3. Ejecutar la escritura, en transacción si cambia varias tablas.
// 4. Registrar Auth::bitacora(...).
// 5. Crear flash y redirigir.
08 · Permisos

Control de acceso

No existen roles fijos. Cada usuario tiene una fila en permisos con banderas independientes.

PermisoHabilitaEjemplos
datosmaestrosInventario, empleados y catálogos.Crear/editar/inactivar equipos, empleados, áreas, cargos, marcas y modelos.
transaccionesOperación de custodia.Asignar, editar una asignación abierta, firmar entrega y devolver equipo.
consultasVistas de consulta.Consultar inventario, empleados y asignaciones sin alterar datos.
reportesListados y descargas.Reportes PDF de empleados, equipos y asignaciones.
actasConsulta documental.Abrir actas ya creadas sin poder ejecutar transacciones.
seguridadAdministración del sistema.Usuarios, permisos y bitácora.
Regla especial de actas. Los GET de actas aceptan actas o transacciones. Los POST que guardan firmas o cierran devoluciones requieren transacciones.
No basta con ocultar el menú. Cada archivo invocable directamente —página, controlador, AJAX o descarga— debe validar el permiso por sí mismo.
09 · Base de datos

Tablas y relaciones principales

TablaPropósitoRelaciones relevantes
empleadosDatos personales, correo, foto y bandera activo.Apunta a cargos, areas y sexo; recibe asignaciones y usuarios.
equipoActivo físico, compra, garantía, serie, código y estado.Apunta a marca y modelo; recibe asignaciones.
asignacionHistorial de entrega y devolución.Relaciona empleado, equipo y usuario de devolución; conserva firmas y checklist.
usuariosCredencial vinculada a un empleado.Uno a uno lógico con permisos; genera entradas de bitácora.
permisosBanderas de autorización por usuario.Se carga en sesión al iniciar sesión.
bitacoraAuditoría de acciones.Referencia al usuario que ejecutó la acción.

Estados del equipo

CódigoEstadoUso
1DisponiblePuede asignarse.
2AsignadoTiene una asignación activa; no puede asignarse otra vez.
3En mantenimientoNo está disponible; también se usa al devolverlo con daño o no funcional.
4Perdido o robadoNo puede asignarse.
5Dado de bajaFuera del inventario operativo; normalmente activo = 0.

equipo.activo controla la baja lógica del registro y equipo.estado_equipo describe su situación operativa. Son conceptos distintos y deben mantenerse coherentes.

Campos clave de asignacion

  • activa = 1 significa que el empleado todavía conserva el equipo; activa = 0 es historial cerrado.
  • fecha_asignacion abre el ciclo y fecha_devolucion queda NULL hasta el cierre.
  • Los campos de entrega conservan condición, accesorios, observaciones, firma y fecha de firma.
  • Los campos de devolución conservan condición, observaciones, firma, usuario y fecha.
  • requiere_firma_entrega permite exigir firma en asignaciones nuevas sin bloquear registros históricos.
No borre el historial. Empleados, equipos, catálogos y asignaciones usan inactivación o cierre lógico. Un DELETE físico rompería auditoría, reportes y relaciones históricas.
10 · Módulos

Comportamiento de cada área

Panel de inicio

index.php calcula equipos registrados y disponibles, asignaciones activas, empleados activos, alertas, movimientos y accesos rápidos según permisos. La sección detallada de estados de equipo existe pero está temporalmente deshabilitada mediante $mostrarEstadoEquipos = false.

Empleados

  • Valida correo y fotografía; relaciona cargo, área y sexo.
  • La “eliminación” establece activo = 0.
  • No permite inactivar a un empleado con asignaciones abiertas.
  • Tampoco permite inactivarlo si conserva un usuario activo.
  • Un empleado inactivo se puede reactivar sin recrear su historial.

Equipos

  • Después del INSERT genera el código único EQ-0001 usando el identificador recién creado.
  • Valida serie, tipo, estado, fechas y costo antes de escribir.
  • Si existe asignación abierta, el estado se fuerza a Asignado.
  • Un equipo no puede darse de baja mientras tenga una asignación activa.
  • La baja lógica coloca el estado en Dado de baja; la reactivación lo devuelve a Disponible.

Usuarios y permisos

  • La creación de usuario y su fila de permisos ocurre en una transacción.
  • La contraseña se almacena con password_hash(); al editar, dejarla vacía conserva el hash existente.
  • No se permite inactivar al usuario con el que se está trabajando.
  • No se reactiva un usuario si su empleado está inactivo.
  • El permiso de transacciones implica acceso a actas; actas permite solo consulta documental.

Catálogos

Áreas, cargos, marcas y modelos usan baja lógica. Los formularios de empleados/equipos también pueden crear ciertos catálogos de forma contextual y agregar la nueva opción al selector sin abandonar la operación.

Bitácora

Registra quién hizo qué, en qué módulo, con qué detalle, desde qué IP y cuándo. Al agregar una operación relevante, agregue también su llamada a Auth::bitacora().

11 · Asignaciones y firmas

El flujo de negocio más importante

Crear una asignación

Comprueba empleado activo.
Bloquea y comprueba equipo activo y Disponible.
Evita otra asignación abierta para el mismo equipo.
Inserta asignación activa con checklist y firma requerida.
Cambia el equipo a Asignado y confirma.

Las verificaciones y el cambio de estado deben permanecer en la misma transacción. El bloqueo FOR UPDATE evita que dos usuarios asignen simultáneamente el mismo equipo.

Firmar la entrega

  1. El empleado firma en un canvas del navegador.
  2. JavaScript envía una Data URI PNG/JPEG.
  3. PHP comprueba formato, tamaño máximo de 2 MB, decodificación estricta, MIME y dimensiones.
  4. Se genera un nombre seguro y se escribe con bloqueo.
  5. La base guarda el nombre y la fecha. Una firma existente no se sobrescribe.

Devolver el equipo

Exige asignación activa.
Si es nueva, exige firma de entrega previa.
Recibe condición, observaciones y firma de devolución.
Cierra asignación, fecha y usuario de devolución.
Equipo queda Disponible o En mantenimiento.
Condición de devoluciónEstado resultante del equipo
BuenoDisponible (1)
Con dañoEn mantenimiento (3)
No funcionalEn mantenimiento (3)
“Eliminar asignación” no existe. Cerrar la custodia siempre significa devolver equipo: completar datos de devolución, guardar la firma, marcar activa = 0 y conservar la fila para siempre.
Archivos históricos. requiere_firma_entrega = 0 permite devolver asignaciones antiguas sin firma previa. Las nuevas deben crearse con el indicador activo.
12 · Frontend y AJAX

Cómo se construye la interfaz

app/views/layouts/head.php carga Bootstrap 5.3, Font Awesome, Inter, DataTables, Toastr y jQuery. Bootstrap ya no depende de jQuery; el proyecto lo conserva porque DataTables y los módulos AJAX actuales todavía lo utilizan. La mayor parte llega desde CDN, de modo que algunas mejoras visuales o tablas pueden degradarse sin conexión a Internet.

ArchivoResponsabilidad
public/css/app.cssEstilos generales, navegación, panel, tarjetas, tablas, formularios y adaptación responsive.
public/css/login.cssPantalla de autenticación.
public/js/ajax-loader.jsEnvía búsquedas POST, espera 300 ms al escribir y coloca la respuesta HTML en #datos.
public/js/catalogos-contextuales.jsCrea o reactiva catálogos desde un modal y actualiza el <select> correspondiente.

Contrato de un endpoint AJAX

  • Debe cargar bootstrap y validar sesión y permiso aunque la página padre ya los haya validado.
  • Debe validar CSRF si escribe. Una búsqueda de solo lectura puede omitirlo.
  • Debe escapar datos impresos con htmlspecialchars().
  • Si devuelve JSON, debe fijar Content-Type: application/json y una estructura estable.
  • Si devuelve HTML, no debe incluir nuevamente toda la cabecera de la aplicación.
13 · Reportes y actas

Generación de PDF

Los reportes de empleados, equipos y asignaciones consultan la misma base y generan documentos con TCPDF. reportes/pdf_layout.php centraliza encabezado, logotipo local, tipografía, pie y elementos visuales comunes.

  • Use public/icons/logo_pdf.jpg para los PDF; no dependa de recursos del sistema operativo ni de URLs externas.
  • No imprima espacios, HTML ni mensajes antes de llamar a la salida de TCPDF; cualquier salida previa puede corromper el archivo.
  • Las actas se diferencian de los listados: representan una asignación específica e incorporan condiciones y firmas.
  • GET de un acta es consulta; POST de una firma es una transacción y requiere validación CSRF.
Para cambiar el diseño. Modifique primero reportes/pdf_layout.php si el cambio debe afectar todos los documentos. Toque un descargador individual solo cuando el contenido sea exclusivo de ese reporte.

15 · Cómo modificar

Procedimientos seguros para cambios comunes

Agregar un campo a un módulo

  1. Cree una migración SQL pequeña, repetible cuando sea posible, y respalde la base.
  2. Agregue el campo al formulario de alta y edición.
  3. Normalice y valide el valor en el controlador; no confíe solo en validación HTML.
  4. Inclúyalo en INSERT y UPDATE mediante parámetros preparados.
  5. Actualice tabla AJAX, consultas, reportes PDF y actas que deban mostrarlo.
  6. Pruebe valor normal, vacío, demasiado largo, duplicado y manipulado.

Agregar un módulo

  1. Defina tabla y relaciones.
  2. Elija un permiso existente o agregue uno a base, sesión, formulario de permisos y todas las rutas.
  3. Cree entrada de página, controlador, formulario y tabla AJAX siguiendo un módulo parecido.
  4. Use baja lógica si el registro puede aparecer en el historial.
  5. Agregue bitácora en altas, cambios, activaciones e inactivaciones.
  6. Agregue el enlace al menú únicamente para usuarios autorizados.

Cambiar una regla de asignación

Revise conjuntamente el controlador de asignación, el AJAX del formulario, las dos actas, las consultas, los reportes y los estados de equipo. Una regla aplicada solo en JavaScript puede evadirse; una regla aplicada solo al crear puede romper la devolución.

Cambiar el diseño

  • Interfaz general: public/css/app.css.
  • Login: public/css/login.css.
  • Encabezado y dependencias: app/pages/head.php.
  • PDF comunes: reportes/pdf_layout.php.
  • No edite archivos dentro de TCPDF salvo que esté actualizando conscientemente la biblioteca.

Checklist antes de guardar código

  • ¿La ruta exige sesión y el permiso correcto?
  • ¿Cada POST verifica CSRF?
  • ¿La entrada fue validada en servidor?
  • ¿SQL usa parámetros preparados?
  • ¿Varias escrituras dependientes están en una transacción?
  • ¿La salida HTML está escapada?
  • ¿La operación queda en bitácora?
  • ¿Se preserva el historial?
16 · Cómo probar

Recorrido funcional recomendado

El proyecto no contiene actualmente una suite automatizada completa. Cada cambio debe acompañarse al menos de validación sintáctica y un recorrido manual con datos de prueba.

  1. PHP: ejecute php -l archivo.php en cada archivo modificado.
  2. Sesión: pruebe usuario activo, credenciales incorrectas, cierre de sesión y acceso directo sin autenticar.
  3. Permisos: pruebe la URL directa con un usuario que no tenga el permiso, no solo la visibilidad del menú.
  4. Catálogos: cree, edite, inactive, reactive y cree desde un formulario contextual.
  5. Empleado: cree uno con correo, edítelo, vincule usuario y verifique que las dependencias impidan inactivarlo.
  6. Equipo: cree uno y compruebe código EQ, serie, estados, garantía, baja y reactivación.
  7. Asignación: asigne solo un equipo Disponible a un empleado activo; intente duplicarlo y confirme el rechazo.
  8. Firmas: firme entrega, compruebe que no se sobrescriba y abra el acta con permiso actas.
  9. Devolución: compruebe que una asignación nueva sin firma no cierre; luego firme y devuelva en cada condición.
  10. Historial: confirme que la fila cerrada sigue visible y que el equipo termina Disponible o En mantenimiento.
  11. PDF: abra y descargue los tres reportes y ambas actas; revise logo, saltos de página y caracteres españoles.
  12. Bitácora: confirme que las acciones ejecutadas aparezcan con usuario y detalle correctos.
Datos aislados. Use registros claramente identificados como prueba y una copia de base separada cuando evalúe migraciones o reglas destructivas.
17 · Reglas críticas

Lo que un cambio nunca debe romper

  • Un equipo solo puede tener una asignación activa.
  • Solo un equipo activo y Disponible puede asignarse.
  • Asignación activa y equipo Asignado deben coincidir.
  • La devolución cierra el registro; nunca lo elimina.
  • Las nuevas asignaciones necesitan firma de entrega antes de devolución.
  • Una firma registrada no se reemplaza silenciosamente.
  • Un empleado con asignación abierta no se inactiva.
  • Un equipo con asignación abierta no se da de baja.
  • Un usuario no se reactiva si su empleado está inactivo.
  • Contraseñas, tokens CSRF y datos de sesión nunca se imprimen ni se guardan en bitácora.
  • Cada endpoint valida autorización; la interfaz visual no es una barrera de seguridad.
  • Los cambios coordinados en más de una tabla se confirman o revierten juntos.
18 · Deuda técnica

Detalles pendientes detectados

Estos puntos no impiden el funcionamiento probado, pero conviene resolverlos antes de exponer la aplicación fuera de una red controlada.

Términos del proyecto

Activo

Equipo físico administrado por la organización. No debe confundirse con la bandera activo de una fila.

Asignación

Periodo durante el cual un empleado tiene bajo su custodia un equipo.

Acta

Documento PDF de una entrega o devolución específica, con condiciones y firma.

Baja lógica

Cambiar una bandera para excluir un registro de la operación sin borrar su historial.

CSRF

Token de sesión que demuestra que un POST fue originado desde un formulario legítimo de la aplicación.

Catálogo contextual

Área, cargo, marca o modelo creado desde otro formulario sin abandonar el registro principal.

Flash

Mensaje guardado temporalmente en sesión y mostrado después de una redirección.

Invariante

Regla que debe ser cierta antes y después de cualquier operación, como “un equipo no tiene dos asignaciones activas”.
